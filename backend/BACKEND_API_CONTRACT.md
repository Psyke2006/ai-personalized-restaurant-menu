# Backend API Contract and Frontend Integration

The repository-root `API.md` is canonical. This document summarizes its requirements and highlights issues to reconcile. Do not silently change the contract. If an update is necessary, coordinate with the frontend owner and update root `API.md` in the same pull request.

## Base URL

`http://localhost:8000/api/v1`

The frontend uses `NEXT_PUBLIC_API_BASE_URL` with that default. Confirm the FastAPI router mounts all routes under `/api/v1`, including health, so `GET /api/v1/health` works.

## Required endpoints

### 1. Health

`GET /health`

Expected example response:

```json
{
  "status": "healthy",
  "version": "1.0.0",
  "recommender_engine": "active"
}
```

### 2. Profile

`POST /users/profile`

Request:

```json
{
  "name": "Example User",
  "budget": 500.0,
  "spice_tolerance": 3,
  "health_goal": "high_protein",
  "dietary_preferences": ["vegetarian"],
  "allergies": ["peanuts"],
  "favorite_cuisines": ["Indian"],
  "favorite_ingredients": ["paneer"]
}
```

Return the persisted profile with an `id` and the same fields. The current example ID is prefixed `u-...`, while prose says UUID. Resolve this inconsistency with the team: ideally use one documented opaque string format across all endpoints, and never assume the frontend can parse it as a raw UUID.

`GET /users/{user_id}` returns the same profile shape or a structured 404 error.

### 3. Manual menu

`POST /menu/manual`

Request:

```json
{
  "restaurant_name": "Spice Bistro",
  "dishes": [
    {
      "name": "Paneer Tikka",
      "description": "Grilled paneer with spices",
      "price": 280.0,
      "cuisine": "Indian",
      "ingredients": ["paneer", "yogurt", "bell pepper"],
      "diet_type": "vegetarian",
      "spice_level": 3,
      "health_tags": ["high_protein"]
    }
  ]
}
```

The current documented response contains `menu_id`, `restaurant_name`, `total_dishes_added`, and `created_at`.

**Contract gap:** the response does not include dish records or IDs. The frontend needs stable IDs and access to all menu dishes after creation. Prefer an additive response that includes `dishes` with stable IDs, or provide a documented `GET /menus/{menu_id}` endpoint. Do not add an undocumented endpoint without coordinating the canonical API update.

### 4. Upload menu

`POST /menu/upload`

Request uses `multipart/form-data`:
- required `file` (supported PDF or image)
- optional `restaurant_name`

Do not require a JSON content-type header for multipart requests.

The documented response includes:

```json
{
  "menu_id": "m-example",
  "extracted_dishes_count": 1,
  "status": "extracted_and_parsed",
  "dishes": [
    {
      "id": "d-001",
      "name": "Paneer Tikka",
      "price": 280.0,
      "cuisine": "Indian",
      "ingredients": ["paneer", "yogurt"],
      "diet_type": "vegetarian",
      "spice_level": 3,
      "health_tags": ["high_protein"]
    }
  ]
}
```

Persist each extracted dish under the menu and return the persisted IDs. Validate Gemini/OCR output before writing it to the database. Report parsing warnings when fields are uncertain.

### 5. Ranking

`POST /recommendations/rank`

Request:

```json
{
  "user_id": "u-example",
  "menu_id": "m-example"
}
```

The documented response contains:
- `user_id`
- `recommended_dishes[]`: `dish_id`, `name`, `price`, `cuisine`, `match_score`, `compatibility_status`, `match_reasons[]`
- `filtered_dishes[]`: `dish_id`, `name`, `price`, `compatibility_status`, `exclusion_reasons[]`

Scores should be numeric percentages from 0 to 100, calculated by the deterministic backend scorer, not generated by Gemini.

**Contract gap:** the response does not explicitly return compatible dishes that were not recommended/top-ranked. Because the product must preserve the complete menu, make all menu items available to the frontend. Preferred resolution: add `all_dishes` or `other_compatible_dishes` to the response with stable IDs and status, or document a menu retrieval endpoint. Keep existing response keys to avoid breaking the frontend.

Compatibility statuses and uncertainty states should be explicit and documented. Coordinate exact enum strings with the frontend owner before changing them.

### 6. Feedback

`POST /feedback`

Request:

```json
{
  "user_id": "u-example",
  "dish_id": "d-example",
  "liked": true,
  "rating": 5
}
```

Validate rating as integer 1–5, ensure referenced user and dish exist, persist feedback, and return the documented `feedback_id`, `status`, and `message`.

Confirm whether `liked` and `rating` are both required. Current API example supplies both; until changed, accept and validate both.

### 7. Errors

Root `API.md` defines this shape:

```json
{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "Requested resource was not found.",
    "timestamp": "2026-10-09T20:10:00Z"
  }
}
```

Maintain a consistent shape for handled errors, including 400, 404, 422, and 500. FastAPI's default validation response differs from this structure, so add a validation exception handler if the canonical contract requires every error to use the documented envelope. Never return stack traces or secrets.

## Cross-cutting requirements

- Configure CORS for `http://localhost:3000` in development; make allowed origins configurable.
- Use Pydantic schemas as the source of truth for request/response validation.
- Keep JSON field names exactly as documented (snake_case).
- Keep IDs stable across profile, menu, dish, and feedback calls.
- Use UTC timestamps with timezone information.
- Ensure OpenAPI output and `/docs` reflect actual endpoint behavior.
- Keep API keys server-side.
- Test requests from the frontend origin, not only with direct Python calls.

## Contract decisions to agree with frontend owner

1. Stable ID format: opaque strings or UUID strings; choose one and document it.
2. Manual menu creation: include persisted dish records in response or add a menu retrieval endpoint.
3. Complete menu after ranking: include non-recommended compatible dishes or provide menu retrieval.
4. Status enum: define exact values for compatible, filtered, and needs-verification.
5. Missing ingredient metadata: specify warning/status behavior; never imply guaranteed safety.
6. Health path and router prefix.
7. Whether profile POST creates only or also updates an existing profile.
