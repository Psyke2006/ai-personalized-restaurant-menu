# Backend Testing Checklist

## Unit tests: filtering

- [ ] Case-insensitive allergen matching.
- [ ] Whitespace and common punctuation normalization.
- [ ] Exact/token-aware matching avoids obvious false positives.
- [ ] Known allergen alias cases are tested.
- [ ] A dish with a matching declared allergen is filtered.
- [ ] Strict dietary violations are filtered.
- [ ] Compatible dishes are not accidentally removed by soft preferences.
- [ ] Missing/unknown ingredient data creates an uncertainty status or warning.
- [ ] No LLM call is required to run filtering tests.
- [ ] Filtered dishes include explicit exclusion reasons.

## Unit tests: scoring

- [ ] Score is numeric and within 0–100.
- [ ] Scores are deterministic for identical inputs.
- [ ] Weights match `ARCHITECTURE.md` and sum to 1.0.
- [ ] Budget at limit and over budget are tested.
- [ ] Spice tolerance boundaries 1 and 5 are tested.
- [ ] Missing cuisine/ingredient/health metadata has defined behavior.
- [ ] Feedback absence and positive/negative feedback have defined behavior.
- [ ] Only dishes passing hard constraints are scored as recommendations.
- [ ] Reasons correspond to actual scoring signals.
- [ ] Stable tie-breaker produces repeatable ordering.
- [ ] Scores are not generated by Gemini.

## API tests

- [ ] `GET /api/v1/health` returns expected fields.
- [ ] Valid profile can be created and retrieved.
- [ ] Invalid budget and spice tolerance return documented errors.
- [ ] Valid manual menu is persisted.
- [ ] Manual menu response provides stable dish IDs or documented retrieval path.
- [ ] Valid PDF upload is parsed and persisted.
- [ ] Valid image upload is parsed and persisted where OCR is configured.
- [ ] Invalid file types and oversized files are rejected.
- [ ] Gemini timeout/invalid output produces a controlled response.
- [ ] Ranking rejects unknown user/menu IDs with structured 404.
- [ ] Ranking returns recommendations and filtered dishes with stable IDs.
- [ ] Complete menu remains retrievable after ranking.
- [ ] Feedback rejects invalid rating and unknown IDs.
- [ ] Errors use `{ "error": { "code", "message", "timestamp" } }`.
- [ ] CORS permits the configured frontend origin.
- [ ] No endpoint exposes environment secrets or stack traces.

## Integration and safety scenarios

1. User with peanut allergy + dish explicitly containing peanuts: dish is flagged, never recommended.
2. User with a strict vegetarian preference + known meat dish: dish is flagged.
3. Dish has no ingredient list: UI/API indicates uncertainty; system does not call it allergy-safe.
4. All dishes are filtered: all remain visible with reasons and the response is valid.
5. Menu has compatible but low-scoring dishes: full menu remains available.
6. Empty extraction: no fabricated dishes; explicit status/error is returned.
7. API key missing or provider unavailable: clear controlled failure or documented fallback.
8. Database write fails midway: transaction prevents inconsistent partial menu data.
9. Frontend uploads a file: browser-generated multipart boundary is accepted.
10. Repeated ranking calls for the same profile/menu return stable ordering when no data changes.

## Test reporting

For every run, report:
- exact command,
- passed/failed/skipped counts,
- environment assumptions,
- known untested cases.

Never invent test outcomes.
